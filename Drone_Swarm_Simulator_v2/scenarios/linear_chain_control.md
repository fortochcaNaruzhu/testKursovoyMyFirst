# Управление в сценарии `linear_chain`

Этот документ описывает, **как устроено управление** в сценарии `scenarios/linear_chain.py`: какие циклы работают, как формируются целевые точки для дронов в «линейной цепи», и как ошибки по положению превращаются в RC-команды.

## Идея сценария

Рой дронов формирует **цепочку с равными промежутками** на отрезке \(A \rightarrow B\) в плоскости \(XY\).

- **Крайние дроны** (с минимальным и максимальным `id`) выступают «якорями» и летят к фиксированным точкам \(A\) и \(B\).
- **Внутренние дроны** управляются **децентрализованно**: каждый находит своих ближайших соседей вдоль отрезка \(A \rightarrow B\) (по проекции на направление отрезка) и стремится к **середине между соседями**.

В результате распределение стабилизируется к почти равномерному: каждый внутренний дрон оказывается посередине между двумя соседями, а крайние удерживают границы.

## Быстрый запуск (важно про окружение)

Сценарии симулятора нужно запускать внутри виртуального окружения проекта:

```bash
source ../drone_env/bin/activate
python Drone_Swarm_Simulator_v2/scenarios/linear_chain.py --drones 6 --segment-length 8 --exchange-hz 50
```

## Архитектура потоков и циклов

Сценарий запускает несколько параллельных потоков:

- **Инициализация каждого дрона** в отдельном потоке (`initialize_drone_parallel`)
  - подключение, арming, takeoff, переход в `POS_HOLD`
  - включение стримов позиции/аттитюда
  - запуск keepalive для RC override
- **Обмен координатами** общим потоком (`coordinate_exchange_loop`, типично 50 Гц)
  - опрашивает текущие позиции всех контроллеров
  - переводит их в «общую» систему координат (см. ниже)
  - для каждого контроллера обновляет позиции остальных через `update_other_drone_position`
  - опционально публикует позиции во внешний 2D-визуализатор (если доступен)
- **Контрольное поведение** — по одному потоку на дрон:
  - для левого/правого якоря — `endpoint_loop`
  - для внутренних — `internal_chain_loop`

Остановка:

- по `--duration` (если задано \(> 0\)); иначе — пока не прервёте процесс (Ctrl+C)

## Системы координат и «общий кадр»

В SITL у каждого дрона «дом» (home) имеет искусственный сдвиг по оси East, поэтому локальные координаты разных дронов **не совпадают**.

Чтобы внутренние дроны могли сравнивать позиции друг друга, сценарий вводит **общий кадр** (common frame):

- локальная позиция дрона берётся как `controller.get_my_position()`
- затем корректируется:
  - `y_common = y_local + (did - 1) * 2.0`

Это делается функциями:

- `_my_position_common(controller)` — получить свою позицию в common frame
- `_did_offset_y(did)` — величина сдвига

Важно: когда вычислена целевая точка **в common frame**, при формировании команды нужно помнить, что конкретный дрон физически летит в своём локальном кадре. В этом сценарии целевая точка для ошибок считается в common frame, но сами RC-команды выдаются по ошибкам, рассчитанным относительно common frame (см. ниже).

## Формирование фиксированных концов отрезка \(A\) и \(B\)

После взлёта сценарий выбирает якоря:

- `endpoint_left_id = min(ids)`
- `endpoint_right_id = max(ids)`

Затем строит конечные точки отрезка:

- `_segment_endpoints_common_from_anchors(anchor_left_common, anchor_right_common, length_m)`
- логика: \(x_A = -L/2\), \(x_B = +L/2\), а \(y\) берётся из текущего \(y\) якорей (после взлёта)

Так отрезок имеет «правильное» 2D-направление в \(XY\) (а не только по \(X\)), и внутренние дроны выравниваются по реальной геометрии.

## Общая схема RC-управления (roll/pitch) через PID

Все петли управления в итоге вызывают `_move_towards_common_with_pid(...)`.

Внутри:

- вычисляется ошибка по XY относительно **целевой точки в common frame**:
  - `err_x = target.x - my.x`
  - `err_y = target.y - my.y`
- применяется deadband `ERROR_DEADBAND_M`
- если расстояние меньше порога (для разных ролей пороги разные) — отправляется нейтральный RC и PID сбрасывается
- иначе PID регуляторы дают два управляющих воздействия:
  - `pitch_output = pitch_pid.update(err_x)`
  - `roll_output = roll_pid.update(err_y)`
- маппинг на RC override:
  - `pitch = RC_NEUTRAL - pitch_output` (вперёд/назад по \(X\))
  - `roll  = RC_NEUTRAL + roll_output`  (влево/вправо по \(Y\))
  - далее clamp в [1100..1900] и отправка `send_rc_override(roll, pitch, neutral, neutral)`

Таким образом:

- управление по \(X\) реализуется через pitch
- управление по \(Y\) — через roll

## Управление крайними дронами (якорями): `endpoint_loop`

Цель якоря — прийти в фиксированную точку \(A\) или \(B\) и затем удерживаться (через отправку нейтральных RC).

Особенности настройки:

- по \(X\) используется более агрессивный коэффициент (`ENDPOINT_X_KP`), чтобы уверенно «разъехать» отрезок
- по \(Y\) — более мягкий (`ENDPOINT_Y_KP`), чтобы избежать «облётов»/раскачки вокруг траектории
- достижение определяется по `ENDPOINT_REACHED_THRESH_M`

Пока якорь не достиг точки — он постоянно вызывает `_move_towards_common_with_pid(...)` с этими PID.

## Управление внутренними дронами: `internal_chain_loop`

Внутренний дрон не знает «своё место» заранее. Он вычисляет его из позиций остальных:

### 1) Сбор позиций и ожидание якорей

- берётся своя позиция в common frame
- берутся «чужие» позиции из `controller.get_other_drones_positions()` (они уже хранятся как common frame, потому что обмен делается в `coordinate_exchange_loop`)
- если оба якоря ещё не видны — отправляется нейтральный RC и цикл ждёт дальше

### 2) Переход к координате вдоль отрезка: проекция \(s\)

Вычисляется единичный вектор направления отрезка \(u\) в плоскости XY:

- `u = _unit_vector_xy(A, B)`

Далее для каждого дрона считается скалярная проекция на направление отрезка:

- `s(did) = _projection_s(A, u, pos(did))`

Это превращает задачу «расположения на линии» в одномерную: **упорядочить дронов по \(s\)**.

### 3) Выбор соседей и стабилизация соседства

Дроны сортируются по \(s\) (с доп. сортировкой по `id` для стабильности):

- `ids_sorted = sorted(... key=(s, id))`

Для текущего `my_id` выбираются соседи:

- `left_id = ids_sorted[idx - 1]`
- `right_id = ids_sorted[idx + 1]`

Чтобы избежать «перескоков» соседей при почти равных проекциях (шум, дрожание), вводится **гистерезис соседей**:

- если новое соседство отличается от предыдущего, оно принимается только если разница достаточно «очевидна» (`NEIGHBOR_HYSTERESIS_M`)

### 4) Целевая точка = середина между соседями

Целевая проекция:

- `s_target = 0.5 * (s(left) + s(right))`

Затем цель ограничивается диапазоном \([s(A), s(B)]\), чтобы не «уехать» за якоря.

После этого target в common frame восстанавливается обратно в 2D:

- `target = A + u * s_target` (в XY), `z = -TAKEOFF_ALT_M`

### 5) Сглаживание цели

Чтобы внутренний дрон не «гонялся» за дёргающейся целью (из-за шума позиций соседей), применяется экспоненциальное сглаживание:

- `target = alpha * prev_target + (1-alpha) * new_target`
- параметр `TARGET_SMOOTHING_ALPHA` (чем больше — тем плавнее и медленнее)

### 6) Дополнительное демпфирование вдоль отрезка (в проекционном пространстве)

Чтобы гасить не затухающие колебания вдоль линии, вводится отдельный PD-закон в координате \(s\):

- ошибка вдоль отрезка: `e_s = s_target - s_me` (с deadband `INTERNAL_S_DEADBAND_M`)
- скорость вдоль отрезка оценивается через монитор скорости:
  - \(v_s = v_x u_x + v_y u_y\)
- управляющее воздействие формируется в «PWM‑шкале»:
  - `u_pwm = Kp*e_s - Kv*v_s`
  - ограничивается `INTERNAL_S_OUTPUT_LIMIT_PWM`
- затем это превращается в **сдвиг цели вдоль отрезка**:
  - `delta_s = u_pwm / INTERNAL_S_KP_PWM_PER_M`
  - `s_target_damped = s_me + delta_s`
  - и снова ограничение на \([s(A), s(B)]\)

Ключевой момент: демпфирование применяется **не отдельной RC командой**, а через **сдвиг целевой точки вдоль линии**, чтобы цель всегда оставалась на отрезке \(A \rightarrow B\).

### 7) Движение к цели через PID roll/pitch

После всех вычислений внутренний дрон вызывает `_move_towards_common_with_pid(...)` с более «мягкими» PID коэффициентами и порогом `INTERNAL_REACHED_THRESH_M`.

## Где смотреть конкретные параметры

В начале `scenarios/linear_chain.py` заданы:

- высота и геометрия: `TAKEOFF_ALT_M`, `SEGMENT_LENGTH_M`
- частоты: `CONTROL_HZ` (управление), `--exchange-hz` (обмен координатами)
- пороги: `ENDPOINT_REACHED_THRESH_M`, `INTERNAL_REACHED_THRESH_M`, `ERROR_DEADBAND_M`
- PID для якорей: `ENDPOINT_X_KP`, `ENDPOINT_Y_KP`, `ENDPOINT_OUTPUT_LIMIT`
- PID для внутренних: `INTERNAL_PID_*`, `INTERNAL_PID_OUTPUT_LIMIT`, `INTERNAL_PID_DERIVATIVE_ALPHA`
- устойчивость соседей/цели: `NEIGHBOR_HYSTERESIS_M`, `TARGET_SMOOTHING_ALPHA`
- демпфирование вдоль отрезка: `INTERNAL_S_*`
